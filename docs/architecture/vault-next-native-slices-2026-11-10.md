Independent read-only inventory; proposals for root selection, not implementation authorization or product activation. Recommend **typed pseudonym-map DAO first, then one atomic agent-approved reminder command**. Custody must precede product wiring, but does not block either isolated synthetic native domain. Neither requires new crypto or another recovery run.

## 1. Typed encrypted pseudonym-map versions

**Real-flow gap.** H3 loses maps on process exit. Its exact current trusted API is `createPseudonymStore().protect({scope,messages,entities,provenance?})`, `restore({scope,text,mappingVersion})`, `restoreStream({scope,mappingVersion,chunks,signal?})`, `exportSnapshot({scope})`, `importSnapshot({scope,snapshot})`, and `rollback({scope,toVersion})` (`server/privacy/pseudonyms.mjs:55`, `:75`, `:119`, `:140`, `:155`, `:162`, `:181`). The backing store is `new Map()` at:76. There is **no legacy SQLite map caller or native counterpart**: native `Kind` is only Note/Chat/Document (`crates/lex-vault/src/lib.rs:92`). An opaque note is insufficient to enforce active-version, namespace, immutable-history and lineage invariants.

Current map identity is workspace/matter: H3 checks a non-null thread but drops it from the key (`pseudonyms.mjs:15`, `:54`). Snapshots contain only format/scope/namespace/mappingVersion/entries, not source-document versions or lineage (`:159`). They are plaintext memory objects, not a persistence or authenticated import contract. ADR0003:37–39 additionally requires exact source versions/hashes and lineage. Those bindings must be introduced explicitly, not claimed from the existing snapshot.

**Smallest proposed native contract.** Add typed `commit_pseudonym_version(scope, expected_revision, expected_active_version, version)`; `get_active_pseudonym_version(scope)`; `get_pseudonym_version(scope, version_id)`; and `activate_pseudonym_version(scope, expected_revision, expected_active_version, retained_version_id)`. Version records carry immutable namespace/version IDs, exact entries, serialization version and bounded source references (object/version/text hash/lineage). Native validates strict fields, marker grammar/namespace, duplicate text/marker rejection, scope and reference bindings, entry/version/byte caps, then commits immutable version + active pointer + metadata-only audit + one CAS revision atomically. Reuse H3 limits initially (256 entries/version,64 retained versions/matter); specify UTF-16 versus UTF-8 caps explicitly. Never log entries or originals. No generic plaintext snapshot file import/export port.

Use exact matter/null-thread native scope; the trusted adapter validates the requesting thread and authorizes access before translating to the shared matter map. Do not silently turn arbitrary thread scope into null or make null mean all threads. Stored source references bind lineage; broker/service must additionally establish that references and caller authority are genuine. No text substitution, detector authority or access policy is delegated to this DAO.

**Ownership and acceptance.** Native owner: new `src/pseudonym_maps.rs`, `tests/pseudonym_maps.rs`, narrow `src/lib.rs` registration/schema, README. Contract owner: new synthetic fixture module/test (avoid broad production H3 rewrite). Land sequentially where lib/schema overlap. Adding tables requires a new explicitly versioned fresh-only synthetic schema; reject old schemas until separately designed migration. No new dependency is inherently required. Synthetic acceptance: keyed reopen retains exact composed/decomposed Unicode and markers; active-pointer/history/audit/revision rollback on a real constraint failure; stale CAS and two writers yield one winner; wrong matter/firm/thread, foreign namespace/source lineage, unknown fields, duplicate markers and bounds fail without mutation; rollback then extension never reuses discarded IDs; close rejects; encrypted store/journal canary scan with positive plaintext control. Later adapter tests must prove restart/restore and keep map/provenance out of the complete outbound envelope. Durable DAO success alone does not prove those later tests.

## 2. Atomic approval of exactly `reminder.create`

**Legacy trigger/signatures.** `agent.approve({proposalId})` re-reads pending proposal and current authority/expiry inside `store.transaction(fn)`, executes the target action, then `store.updateAgentProposal(proposal)` and `store.logAgentAction(entry)` (`server/service.mjs:316`–340). For `reminder.create`, dispatch at:285 reaches `createUserReminder(p)` at:237 and `createReminder(m,payload,{source,status,plannerRule})` at:118; that calls `store.createReminder(reminder)` and `store.audit(action,id)` at:123. Legacy DAO signatures are at `server/store.mjs:147`, `:152`, `:155`, `:189`, `:199`, `:203`.

**Native counterpart/gap.** `Vault::commit_agent_changes(scope, creates, updates, actions, expected)` opens and commits its own IMMEDIATE transaction (`crates/lex-vault/src/proposals.rs:273`–348). `create_reminders(scope, reminders, expected)` independently commits another (`src/reminders.rs:158`). Calling these with separate awaits can leave a reminder without its approved decision/log, or a decision without the effect. README:177 explicitly excludes this parity. Implement one typed `approve_reminder_proposal(scope, proposal_id, expected_revision, approved_args_hash, decision_time, reminder_id)` command; derive the reminder from the stored proposal, not a second unconstrained caller payload. Re-read pending/action/scope/args binding/expiry inside one transaction; validate canonical date input or explicitly reject unsupported legacy date spellings. Commit reminder + derived reminder audit + proposal transition/result + derived action log + one revision together. No SQL/callback/function RPC, shell or external side effect. Service authorization remains mandatory; a timestamp/hash parameter is not proof of human approval.

Only `reminder.create` is in scope. Planner fan-out, document import, export, workspace-level matter creation and arbitrary audit parity remain pending. Define repeat approval as returning the already committed same result without creating another reminder or revision; reject mismatched command identity. An expired proposal must have a specified atomic expired outcome with no reminder. Do not loosen native scopes to emulate workspace enumeration.

**Ownership and acceptance.** One native owner: new `src/approved_reminders.rs`, `tests/approved_reminders.rs`, crate-private transaction helpers in `proposals.rs`/`reminders.rs`, narrow `lib.rs` module registration; helpers operate on an existing transaction and never nest commits. Contract owner: fixture/test additions and README; active `service.mjs` remains unchanged. Existing tables may suffice; version schema only if durable idempotency/result representation requires it. Synthetic tests inject failure after reminder, proposal and audit writes and reopen to prove total rollback; race two approvals/CAS; retry after committed-but-lost response returns one effect; reject wrong firm/matter/thread, hash, action, expired or nonpending proposal and payload mismatch; check canonical dates, injection text inertness, append-only logs and encrypted canaries. These are proposed checks, not newly run tests.

## Dependency/order decision

Maps first directly advance confidential-input → substitution → restart → authorized restoration. Approval/reminder second closes one genuine cross-domain transaction without waiting for every legacy kind. **Custody/lock and private broker are the next integration prerequisite**, rather than a reason to block synthetic DAO work: current `SyntheticVault::create/reopen` accepts a generated key and fresh temporary root (`lib.rs:137`, `:163`), while `close` is only one connection (`:435`; README:15). ADR0003:31–33 requires a supervised private Rust connection and bounded asynchronous domain IPC, with independent scope checks; :45–47 requires native key custody and coordinated cancellation/lock. No public store port, production constructor, real key/store or Keychain call belongs in these two slices.

Before either is exposed through F0, implement/review the broker/session/custody boundary and local HTTP Host/Origin policy. ADR0004:7 selects same-origin loopback Node web plus supervised native broker; :15 records missing/absent-Origin/Host limitations; :20–23 makes the boundary and complete protected-request flow explicit. Do not add CORS access or route the memory fixture into production to demonstrate progress. Product migration, full matrix parity, H5/H6, recovery of typed H3 maps and physical8GB acceptance stay open.

Evidence method: local source/document reads only; no datasets, models, keys, customer stores, network, builds, native calls or tests executed for this inventory.
