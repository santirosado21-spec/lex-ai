# S2a — Piloto pareado corregido, protocolo v2

Fecha local: 2026-11-09, America/Mexico_City. El dueño autoriza S2. Este corte implementa y ejecuta un piloto de desarrollo sobre acceso SF gratuito ya confirmado; no registra proveedor de producto ni reutiliza credenciales de desarrollo para clientes. S2 completo conserva aceptación profesional y evaluación de rutas/modelos de producto/budget autorizados.

## Diseño congelado antes de generación

Seis inputs nuevos (tres por task S1), de autor independiente. Son aceptación de este piloto, no los doce fixtures vistos de S1 ni el examen privado retirado; no retocar skills/casos después de observar respuestas. Al publicar/revisar se retiran como aceptación de futuras afinaciones. Dos modelos explícitos Groq `openai/gpt-oss-20b` y `openai/gpt-oss-120b`, ambos observados en catálogo autenticado de esta sesión. Una repetición por caso y brazo: 24 intentos de generación como máximo, sin significación estadística general.

Cada pareja conserva exactamente input, esquema de salida, taskId/requestSha256, modelo, temperatura0, máximo de salida2500 tokens y timeout45000ms. Ambos brazos incluyen instrucciones neutrales idénticas de devolver el contrato JSON, identidad, esquema y campos del input, incluidas las invariantes relacionales del validador S1 que el esquema JSON no expresa (estados/datos faltantes, tipos de evidencia por issue, cobertura, citas y ámbito). Solo `with-skill` añade texto de la skill seleccionada; `without-skill` lo omite. El wrapper SF común permanece igual. Contrabalancear primer brazo por índice caso/modelo, no ejecutar todos los with primero. No dar al modelo IDs de evaluación, expectativas, rúbricas, notas del autor o metadatos ciegos.

No reducir contenido del brazo sin skill por token ni rellenar contexto artificialmente para igualar longitud: el coste adicional de la instrucción es parte del tratamiento. No cambiar fuentes, ventanas, reparación o retries entre brazos. El programa conserva los bytes/cadena exactos del prompt/body de generación sin headers/credencial, digest de cada uno y configuración para auditoría. Verifica identidad del modelo observada exacta; no aceptar alias/fallback silencioso.

## Corpus y revisión

`eval/legal-tasks/s2-v2/cases.jsonl` exacto `{id,input}`. Seis IDs opacos para control local; **solo input** se serializa al modelo. Inputs cumplen S1 y límites; como mínimo dos incluyen pasajes oficiales cortos cotejados por el autor con URL/captura/página/versionId/hash de texto y el resto usa documentos y reglas ficticias. No promover corpus C1a, ni declarar vigencia o applicability por obtener pasaje. Las preguntas y documentos de contratos son inventados. La clase de cada input y fuente se revisa antes del envío; todo queda bajo public/synthetic. No usar secretos, ejemplos de clientes, fuentes con licencia no autorizada o textos de S1 desarrollados vistos como aceptación.

`eval/legal-tasks/s2-v2/rubrics.json` exacto `{schemaVersion:1,status:"frozen-pilot-acceptance",cases:[{id,description,criteria:[{id,description}],sourceEvidence:[{sourceId,url,pages,observedAt,textReviewNote}]}]}`. Rúbricas son para revisión local ciega, no oráculo dentro del prompt. Criterios distinguen fidelidad del contenido, inferencia/contradicciones, límites y abstención; no exigir una frase exacta como sustituto de utilidad. No salida modelo precocinada. `README.md` describe procedencia, límites y reserva de aceptación futura.

Antes de live: autor congela hashes; coordinador verifica procedencia de textos/casos; revisor independiente aprueba arnés/pares/budgets con transporte simulado; freeze conserva los inputs/rúbricas, skills, S1 y código del arnés. No ejecutar live mientras estos puntos estén pendientes.

## Recibos y métricas

Por job: ID local/caso/modelo solicitado/observado/brazo, hashes del input/skill/prompts, hora UTC, elapsed de generación, elapsed total con catálogo, respuesta cruda pública/sintética o categoría de error, finish_reason/usage disponibles. No fabricated usage para fallos. Si hace falta observar fetchImpl para conocer respuesta truncada y headers, delegar a `fetch` con las mismas opciones/AbortSignal del helper; nunca guardar tokens, authorization/otros headers, cuerpos de error remotos o archivos settings. Solo headers de tasa `x-ratelimit-*` permitidos para diagnóstico; no deben incluir secretos.

Persistir progresivamente `plan.json`, `attempts/<jobId>.json` y report final/partial para cada intento. Los headers/model/usage de las respuestas se filtran de forma explícita; no guardar reasoning textual ni mensajes del sistema del proveedor. Captura de request/body solo campos modelo/messages/max_tokens/stream/temperature/provider esperados, sin claves. El texto de respuesta se trata como datos, nunca se ejecuta.

Agregados por modelo/brazo: intentados, completos, fallos/pendientes, JSON/citas/contrato según S1, prompt/completion/total tokens reportados, latencia media/p50/p95 y tamaño de prompt. Mantener denominadores planeados/intentados/parejas completas; p95 con pocas muestras no estimación estable. Coste facturado real permanece desconocido; acceso declarado Free no demuestra auditoría de coste cero. No estimar precios pagados como cargo real ni asignar coste0 a errores sin usage. Tokens de razonamiento/caché solo si proveedor los informa; no contarlos doble en total.

Reportar separately el pase estructural completo versus contenido recuperable: respuesta JSON inválida no se repara, pero puede conservarse para revisión humana con su estado de fallo. IDs/versiones/quote/cobertura válidos no implican precisión jurídica. Revisión SF ciega evalúa criterios sin nombres de modelos/brazos y registro de mapping separado. Se necesita revisión posterior de Lorenzo/Pedro; no declarar validación profesional, ganador producto o ventaja general con seis casos/una repetición.

El directorio ignorado guarda respuestas/model mapping; QA versionado resume evidencia pública/sintética sin secretos. Crear paquete de revisión ciega para abogados por caso con salida A/B, fuentes, rúbrica y formulario pendiente. No contactar a cofounders por herramientas sin instrucción explícita; paquete local es entrega revisable, no revisión humana ejecutada.

## Precisión de diseño antes de observar respuestas

Revisión previa a freeze/live: raíz y revisor detectaron que entregar solo el JSON Schema dejaba reglas mecánicas del validador sin explicar al baseline. Se decidió compartir todas esas reglas de contrato en ambos brazos, sin métodos de investigación/revisión o criterios de calidad del gold. La única diferencia de tratamiento sigue siendo la instrucción de la skill. No se cambiaron casos/rúbricas/S1 ni se observó una sola respuesta de modelo antes de esta precisión. Así el pase de formato no premia simplemente acceso desigual a reglas ocultas.
