# Inventario de datos privados H5a

Fecha: 2026-11-09. Contrato de inventario `h5a-inventory-v1`. Responsable: worker Codex/Sol `inventory_h5a`; decisión de biblioteca, custodia y recuperación: coordinador, [ADR 0003](adr/0003-private-vault.md). Este documento congela la superficie y el contrato que deben implementar H4b/H5b; no implementa cifrado, bloqueo de bóveda ni migración.

Se inspeccionaron fuentes del repositorio y un almacén temporal sintético nuevo. No se abrió `.data`, una base real, documentos del usuario, Keychain ni credenciales. El reporte [vault-inventory-2026-11-09.json](../qa/vault-inventory-2026-11-09.json) liga revisión Git, hashes de fuentes y versiones a la observación. La revisión Git describe el HEAD, no garantiza árbol limpio: los hashes identifican las fuentes efectivamente leídas. No se ejecutó inferencia, Mail, Office, Whisper ni empaquetado nativo.

## Base privada y derivados

`server/store.mjs:createStore(dataDir)` abre `dataDir/lex.sqlite` mediante `node:sqlite.DatabaseSync`, chmod `0600`, directorio `0700`, `foreign_keys=ON`, `journal_mode=DELETE`. No recibe una llave. Migración actual: `user_version` al menos 3 y añade `counterparties` a registros legacy; no es migración criptográfica. Expone `db`, `get/list` sin ámbito opcional y `put`; el servicio añade comprobaciones. No hay aislamiento criptográfico por despacho/asunto en esta API.

## Interfaz congelada de bytes y procedencia para H4b/H5b

Es un **requisito propuesto v1**, no tablas/API implementadas. La biblioteca/formato criptográfico se fija en ADR 0003; no diseñar cifrados, nonces ni envolturas propias aquí. H4b puede depender de este contrato semántico, no de cómo SQLCipher u otra biblioteca guarda páginas.

1. Cada objeto privado tiene `objectId`, tipo, `{workspaceId,matterId,threadId?}`, versión inmutable y revisión transaccional. IDs y nombres originales permanecen dentro del contenido protegido. Chats legacy sin asunto/hilo conservan su ámbito local incompleto: bloquear salida híbrida, nunca asignar wildcard ni asunto global. El store no toma el scope del texto.
2. `originalBytes` conserva secuencia exacta importada; `originalSha256` y longitud se calculan sobre bytes decodificados del base64. Nombre/tipo MIME son metadatos privados distintos del contenido. Extraer conserva `extractorVersion`, digest/versión de dependencia, estado `complete|partial|unsupported|failed`, hash de original, transformación explícita de texto (las actuales NUL/CRLF/trim) y `textSha256` sobre UTF-8 **sin nueva normalización Unicode**.
3. Cada segmento de detección deriva de ese texto/versiones exactos: `segmentId`, ruta de campo, `textSha256`, ámbito verificado, padres `{objectId,version,hash}` y categoría heredada más restrictiva. Rangos UTF-16 semiabiertos y límites de pares sustitutos según [H4a](privacy-classification-v1.md). Índices FTS/chunks se regeneran solo desde la versión vinculada y nunca pierden padre/categoría. Evidencia pública mantiene URL oficial, identificador/artículo, jurisdicción, versión/fecha y fragmento verificable; categorías privadas no se reclasifican por contener citas.
4. JSON de procedencia/manifiesto usa la representación de `server/canonical-json.mjs`: claves ordenadas, arrays en orden, valores JSON finitos, UTF-8 sin normalización/recorte; rechazar getters/ciclos/campos no soportados. Texto y campos deben tener versión/hash antes de detector/protección y volver a comprobarse antes de mostrar/guardar. El cuerpo HTTP final sigue siendo contrato H6 separado; nunca enviar manifiesto/mapa local al proveedor.
5. `snapshotManifest` lógico contiene `formatVersion`, versión de esquema/app/extractor/procedencia/serialización, `vaultId`, ámbito, generación/linaje de snapshot, revisión origen, `objects[]` con tipos/versiones/longitudes/hashes, mapa con namespace+mappingVersion, versión de política y versiones de corpus público referenciado. Incluye originales, JSON, búsquedas o receta/versiones para reconstruirlas, chats/recuerdos/drafts, horas/timers/honorarios, acciones pendientes y metadatos de correo. Las referencias a claves son identificadores opacos, nunca secretos. H5b debe autenticar y proteger manifiesto y hashes (también sensibles); no exponer listas de nombres/ámbitos en una cabecera clara por comodidad.
6. Snapshot consistente requiere detener escritores/acciones por vault, finalizar o cancelar operaciones, capturar una única revisión de base+originales+mapas y publicar atómicamente solo el conjunto completo. Interfaz futura: `saveSnapshot({scope,expectedRevision,...})`, `restoreSnapshot({scope,snapshotId,expectedRevision,mode})`; CAS falla si cambió revisión/mapa/política. El número de revisión monotónico y el linaje de restauración evitan ABA y aplicar resultado en vuelo anterior. No basta copiar `lex.sqlite` mientras está abierta.
7. Restore valida claves/ámbito/versiones/integridad antes de publicar; abre en staging aislado y no mezcla registros. Política sobre escrituras posteriores: detener y rechazar sustitución si revisión activa difiere; conservar rama/copia existente y exigir decisión local explícita para reemplazarla. Tras recuperación, nueva revisión/linaje, invalidar operaciones viejas y revalidar políticas/consentimientos; correo `submitting` sigue `unknown`, trabajos incompletos fallan, temporizadores se reconcilian sin tiempo duplicado. Copiar un consentimiento antiguo no autoriza acciones nuevas.

Si H5b cambia normalización, orden/serialización, esquema de segmentos, extracción, clases heredadas, snapshots o CAS, versionar contrato y repetir mediciones H4b afectadas + H3V. No exige desechar corpus de reglas no afectado. No iniciar integración H6 por documentar esta interfaz.

## Medición H5a y pendientes

Comando reproducible: `node scripts/qa-vault-inventory.mjs --write`; sin flag imprime solo el reporte sanitizado. No acepta ruta de datos. Crea exclusivamente un hijo `lex-vault-synthetic-*` de tmpdir, usa `createStore`, inserta originales/chunks/FTS, historial/recuerdo/correo y horas/timer/honorarios de prueba, inspecciona DB/rollback journal y elimina solo ese hijo verificado. Reporta booleanos/conteos/hashes/versiones, sin bytes/nombres/rutas reales/llaves/prompts. Hash del archivo DB cambia entre corridas por IDs/fechas de auditoría; no exigir hash idéntico para repetir controles.

Medido: Node 22.22.3, SQLite 3.51.3, esquema 3; 18 tablas incluyendo 5 internas FTS, 9 records, 2 originales, 2 chunks y 2 filas FTS, una fila por tiempo/timer/convenio/tarifa. Los 12 controles pasan, incluyendo reapertura sin clave, scope SQL acotado y limpieza de temp. Los **7 controles negativos de texto claro son verdaderos**: cabecera SQLite, original, chunk, nombre, historial, tiempo y preimagen de rollback journal visibles. `cipher_version` devuelve cero filas; ejecutar `PRAGMA key` no impide leer/reabrir sin clave. Esto evidencia ausencia de cifrado en este almacenamiento, no un test de cifrado aprobado. WAL/SHM ausentes en esta corrida no prueban comportamiento tras cambiar modo/biblioteca.

Pendiente: cifrado/custodia/recuperación nativa y exportaciones seguras; inventario dinámico del daemon/Whisper/Office/WebView y crash; pruebas completas del [protocolo H5b](../qa/vault-test-protocol.md), reejecución H3V con persistencia real, revisión especializada, desempeño conjunto y equipo físico de 8 GB. La base H4a no mide Tauri nativo y no se repitió por esta entrega documental/sintética.
