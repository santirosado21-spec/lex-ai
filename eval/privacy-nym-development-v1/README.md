# Nym independent synthetic development v1

These 60 freshly authored Spanish-MX cases are **DEV only**, not the independent 300-case acceptance set. Annotations are proposed silver spans awaiting root and separate reviewer verification. They are not lawyer-reviewed truth, legal/privacy acceptance, permission for egress, training authorization or evidence of model quality. No detector, tokenizer, model, scoring, network or new runtime was executed to create them. Authoring used only the schema/annotation guide, composition protocol and Nym development-plan documents pinned in `manifest.json`; existing development/heldout cases, gold, predictions and results were not consulted. Native model labels/mappings are not gold categories here.

`dev.jsonl` follows the v2 case contract exactly. Each line contains the immutable synthetic scope, representation segments, original UTF16 half-open entity spans, expected status/reason, independent preservation annotations and explicit operational stimuli. A candidate must receive only `{scope,segments,operational}`. Never project `entities`, `preserve`, IDs, split, template groups, expectations or this manifest into candidate input. Public storage does not authorize gold access. Sixty distinct new story IDs identify authoring units; they do not establish statistical independence or disjointness against unread corpora.

All purported people, organizations, addresses, case facts, identifiers and relationships were invented. Accidental resemblance remains possible. Email domains use `.invalid`/`.test`. RFC/CURP/CLABE/account/phone strings are visibly synthetic fixtures, with no registration, checksum, deliverability or validity guarantee. Citation text is a preservation negative control, not a current-law assertion. Operational text, JSON keys and instructions inside segments are inert data.

## Composition and counts

There are 60 cases, 64 segments and 70 entity occurrences across all 12 product-policy categories: person20, organization7, rfc3, curp3, clabe2, account5, email10, phone3, address2, case_id8, context2, sensitive_relation5. Repeated occurrences and contained person/relationship spans are annotated separately. The set is deliberately small and uneven; no acceptance denominator or quality gate is satisfied merely by these counts.

There are 47 expected complete and 13 expected blocked cases. Blocks comprise scope mismatch2, unknown provenance2, unsupported format2, partial extraction2, ambiguity2 and detector failure3. Five complete clean cases have no entity spans; ten blocked cases still contain entities. Visible entities in blocked cases remain annotated and are not perfect recall by virtue of blocking. Fifteen preservation spans cover date6, amount8 and citation1. Actual restoration and amount/date fidelity have not been tested.

Segment surfaces are current text32, history7, metadata5, tool output4, extraction4, filenames3, provider-envelope representation3, path values2, structured/schema representation2, retrieved text1 and derived context1. Case060 combines five surfaces in one request. A filename/path **value** is segment text, while the segment `path` names its representation. Structural-key case050 is inert JSON text containing an email key; successful entity detection does not authorize structural rewriting or a request. Full-request coverage is unvalidated.

Unicode witnesses include an astral symbol before a name, a multi-codepoint emoji sequence, NFD combining accents, nonbreaking space, tabs and CRLF. Ranges address the original text without normalization. Boundary checks reject surrogate splits. Labels exclude external roles/labels and sentence punctuation; proposed context/relation clauses follow the guide, including nested person spans.

## Operational and budget witnesses

Cases036–046 carry explicit foreign scope, unknown origin, processor failure, partial extraction, unsupported media/extraction or ambiguous assessment. Expectations are separate from these stimuli. Cases045–046 intentionally avoid inventing entity/context boundaries. Unsupported native mapping behavior is not predicted: product context/relationship annotations are independent of whether a model supports them, and no mapping or threshold is tuned here.

Case058 has 8,754 text UTF8 bytes and an 8,324-unit UTF16 envelope, plus explicit simulated `processorStatus=failed`. Case059 has 20,242 text UTF8 bytes and a 19,867-unit UTF16 envelope, `processorStatus=ok`, known provenance, supported media and complete extraction. It must be blocked by input admission: it exceeds the v2 7,000-unit envelope and proposed Nym 16,384-byte fixture cap. The expected reason is `detector_failure` for malformed/limit input under v2, not an invented extraction failure. No entity gold is needed for case059. Both cases remain in the planned60 denominator; do not truncate, window, replace or silently skip them. No tokenizer was run, so **512-token overflow is not measured**. Candidate-specific uncertainty/BIO/confidence/offset/unsupported-native failures may cause additional blocks; expected complete means the authored case has no input-policy blocking stimulus, not a guarantee that a candidate can complete it.

## Review and use

Inline stdlib validation checks exact schema fields, allowed categories/statuses, scope/operational consistency, unique IDs, original UTF16 ranges, no surrogate splits, no duplicate annotations, materialized counts and deterministic input budgets. These technical checks do not prove annotation completeness or semantic correctness. Root and a separate reviewer must verify the proposed annotations and freeze dataset/candidate separately before any later diagnostic scoring. This packet grants no execution authorization or freeze, and no acceptance, production, legal-quality, privacy, release-license or physical8GB claim. All earlier failed runs and frozen data remain separate. Manifest hashes bind corpus and source documents; no prior data was copied or revised.
