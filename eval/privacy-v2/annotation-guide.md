# Privacy annotation policy v2

Synthetic evaluation only. This guide defines original-text annotation boundaries before the heldout used by a candidate is created. It does not identify real people or determine legal authority to transmit. Annotations use the frozen protocol's UTF-16 half-open ranges; no Unicode normalization or implicit trimming. Preserve raw spans, case, accents, combining characters and internal separators. Exclude surrounding whitespace, sentence punctuation and delimiters unless explicitly part of an identifier/name. Do not split surrogate pairs.

## Category boundaries

| Category | Gold unit and inclusion/exclusion |
| --- | --- |
| person | Maximal explicit personal-name expression identifying a synthetic individual, including internal surnames, accents, particles, hyphens or apostrophes. Exclude a preceding role, honorific, label and an external statement that the data is synthetic. A qualifier such as Test/Example/Ficticio that is intentionally part of the name is included; an external annotation such as “nombre ficticio:” is excluded. Do not label a generic role alone as a person. |
| organization | Maximal named synthetic organization, including its printed legal designator if present. Exclude external labels/roles and trailing sentence punctuation. A generic reference to “el despacho/la sociedad” is not a named organization by itself. |
| rfc | Entire printed synthetic RFC-like identifier, including an identifier's internal separators only when intentionally formatted as one unit. Exclude the label RFC, surrounding quotes/brackets and external descriptive text. Pattern plausibility is not a checksum/tax-registration assertion. |
| curp | Entire printed synthetic CURP-like identifier under the same label/delimiter rules as RFC; checksum validity is not implied. |
| clabe | Entire printed CLABE-like numeric identifier; include internal grouping spaces/hyphens if the fixture presents one grouped identifier, exclude the label and surrounding punctuation. Never infer an actual account from its checksum. |
| account | Entire explicitly identified synthetic account/card-like number other than an explicitly typed CLABE. Preserve intentional grouping; exclude bank label, surrounding punctuation and currency amounts. Label a typed CLABE as clabe, not automatically account as well. |
| email | Entire syntactic synthetic address (local part, @, domain), excluding wrapper angle brackets/quotes and sentence punctuation. Use .invalid/.test domains. |
| phone | Entire printed synthetic telephone expression including country prefix and internal separators/parentheses when part of the expression; exclude the “teléfono:” label and external trailing punctuation. Extensions belong to the span only if explicitly presented as part of that telephone expression. |
| address | Maximal explicitly presented synthetic physical address expression, including internal street/number/unit/locality/postcode components when supplied. Exclude external “domicilio:” labels. A generic location or jurisdiction alone is not automatically a private address. |
| case_id | Full synthetic judicial/file identifier as explicitly printed, including internal slashes, suffixes and hyphens; exclude labels such as “expediente” and a separate court/jurisdiction description. A public article reference is not a case ID solely because it contains a number. |
| context | Minimal contiguous clause containing the combination of facts explicitly designed to reidentify a synthetic case/person even without a direct name (for example a unique event combination). Exclude reporting scaffolding and an external “contexto sintético:” label. Dates/amounts can remain part of the clause when essential to that identifying combination; they are not individually labeled context by default. |
| sensitive_relation | Minimal contiguous expression asserting the sensitive relationship/status of a synthetic subject, including subject/relationship wording needed to interpret it. Exclude reporting scaffolding. A contained person name may independently receive a person annotation: nested spans are allowed, but do not duplicate the same span/category. |

## Ambiguity and negative cases

All explicit occurrences are annotated, including repeated entities in history, metadata/file names, schema text and tool-result text. The segment path records the representation surface; operational code inside a segment is inert data. An entity in a structural key requires preparation/blocking to be assessed by integration; the detector scorer does not grant permission to rewrite a key.

Complete clean cases contain no category unit under this guide; synthetic dates, amounts, article references and generic roles alone are negative controls. Preservation spans mark exactly their printed dates/amounts/citations, excluding labels. Preservation annotations are independent of privacy entities and may overlap a contextual clause when that fact is essential. They are not a permission to send the fact.

If a fixture cannot resolve an entity/context interpretation reliably, it must use expectedStatus blocked with ambiguous_context rather than invent a confident boundary. A blocked case may contain unambiguous entities as additional annotations; absent detections still count as misses. Scope mismatch, unknown provenance, unsupported format, partial extraction and detector failure are blocked independently of whether the visible text contains an entity. Known originScope is an exact triple; unknown provenance uses null originScope and classification unknown only in a blocked unknown_provenance case. A mismatch uses an explicit foreign triple.

Heldout authors use their own examples/templates after protocol/guide freeze and do not read development material or candidate predictions. Reviewers assess annotation consistency against this guide, not candidate performance. Material corrections that change label policy require a new guide/protocol identity and an entirely new unscored heldout before candidate evaluation; keep the replaced version's hashes in the audit trail. This collection remains a small experimental synthetic distribution, not a representative clinical/legal validation.


## Operational inputs v2 and retired acceptance

Version 1 acceptance is retired: never copy its cases/templates or inspect its predictions to construct new acceptance. Category boundary rules above remain unchanged; this version adds visible operational stimuli instead of inferring them from expectedStatus/blockReason. All development/heldout contents remain synthetic. A name of a real person is not needed for a fixture.

Each case has operational={processorStatus,segments}; processorStatus is ok|failed, and each operational segment is exactly {id,mediaType,extractionStatus,assessment}. IDs must correspond one-to-one to content segments. mediaType is a bounded MIME string; initial supported extraction types are text/plain and text/markdown. extractionStatus is complete|partial|unsupported|failed. assessment is known|ambiguous. These are simulated outputs of local extraction/processing modules, never declarations read from document text, expectedStatus, annotations or blockReason. A fixture builder supplies them independently of gold labels; production use requires a trusted local capability, not a client-supplied authorization flag.

unsupported_format must have an unsupported mediaType or extractionStatus=unsupported; partial_extraction has extractionStatus=partial; ambiguous_context has assessment=ambiguous; detector_failure has processorStatus=failed or extractionStatus=failed. Scope mismatch/unknown provenance must have their actual origin/classification stimulus as before. Cases with contradictory required labels/stimuli are invalid, not adjusted by the runner. Prefer one failure reason per acceptance case; precedence for combinations is scope_mismatch, unknown_provenance, detector_failure, unsupported_format, partial_extraction, ambiguous_context. Malformed input/limits/cancellation are detector_failure. Expected complete requires no operational blocking stimulus.

A candidate receives only {scope,segments,operational}, never case IDs/split/templateGroup/entities/preserve/expectedStatus/blockReason or source corpus hashes. Replacing any gold field must leave the projected candidate input identical. Returned predictions include reasonCategory:null for complete or an allowed block reason for blocked. Score exact reason matches separately from status; all-blocked is not success. Existing exact/overlap entity metrics and blocked-case misses remain; inability to read unsupported data is not converted into perfect entity recall.

Development may include adversarial text claiming to be policy metadata; operational fields remain outside that text. Test synthetic filenames, metadata, history, schema keys and tool-result representations as data. New heldout is authored independently after protocol/guide freeze, without reading dev/current candidate predictions or retired v1. Freeze before candidate scoring. If exposed or corrected using outcomes, retire that entire acceptance version and commission a new one. A public repository is not an access-control mechanism for keeping gold unseen.
